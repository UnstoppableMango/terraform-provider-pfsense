# The Terraform schema follows the spec's field markers, and gen-config adds only what the spec can't say

tfplugingen-openapi builds each resource's schema from the create request body and the read response.
pfSense REST API v2.8.1 reuses one component schema for both, so fields the spec marks `readOnly` (235 of them) end up user-settable: `firewall_rule`'s `tracker`, `created_time` and `updated_by` are `computed_optional` in `gen/schema.json`.
The spec also types `id` and `parent_id` in request bodies as integers, although GET accepts an integer or a string and parent ids such as `lan` are strings.
It doesn't say which fields can't change after create (`editable: false`, visible only in the REST API source), and parent models embed their children: 22 models carry a nested-model field, such as the DHCP server's `staticmap`, `pool` and `numberoptions`.
Decided in [#66](https://github.com/UnstoppableMango/terraform-provider-pfsense/issues/66); Keys and the Lookup are [ADR 0001](0001-resources-are-identified-by-key-not-api-id.md), the resource list is [ADR 0002](0002-resources-are-derived-from-endpoint-metadata.md), and the apply flags are [ADR 0003](0003-every-write-applies-in-the-same-request.md).

## Decision

- `cmd/patch-openapi` strips every `readOnly` property from request bodies, so those fields become computed-only attributes: kept in state, never set by the user.
- `writeOnly` fields, such as passwords and keys, are sensitive attributes. pfSense never returns them, so Read keeps the value already in state.
- A change to any Key field, or to a field on the **create-only** list in `cmd/gen-config`, forces replacement. The list is taken from `editable: false` in the REST API source at the pinned tag, the same way Keys are; at v2.8.1 that's about 12 writable fields, such as firewall rule `floating`, VLAN `if`, interface group `ifname`, and the certificate revocation list's `caref`, `method` and `text`.
- `id` is not a Terraform attribute. The resource id is the Key, and the generated request code puts the API id from the Lookup into each request.
- `cmd/patch-openapi` retypes `parent_id` in request bodies to a string. It stays a required attribute and forces replacement.
- A nested-model field whose model is generated as its own child resource is dropped from the parent's schema and never sent. PATCH leaves omitted fields unchanged, so writing a parent can't wipe its children. Nested objects that are not resources become nested attributes, tfplugingen's default.
- A Marker-keyed resource's request and response mapping, generated by `cmd/patch-provider`, appends the Marker to `descr`/`description` on write and strips it on Read. The Key declaration in `gen-config` switches it on.
- The rule is the same for every derived model. `gen-config` carries only what the spec can't express: Keys, the create-only list, and the list of models whose writes stay asynchronous (ADR 0003).

## Considered options

- Per-model attribute overrides in `gen-config`: rejected, the spec's own markers cover the common cases, and per-model lists would grow with every re-pin.
- Keeping embedded children on the parent as well as generating child resources: rejected, two resources would own the same objects and fight over them.
- Fixing `id`/`parent_id` in the request code only: rejected for `parent_id`, which the user sets and has to be a string attribute; `id` is simply removed.

## Consequences

- Patching the spec changes `gen/schema.json`, so the schema drift check moves with it.
- Drift on write-only fields can't be detected.
- The create-only list has to be checked against the source when the pin moves, like the Keys.
- Which computed attributes still produce a non-empty plan after apply, because pfSense fills in defaults, is left to a later decision.
